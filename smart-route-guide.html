PolyDeck · 网关功能

智能路由使用说明

按请求内容自动把活儿分给对的模型：架构与财务走强模型，CRUD 与文档走快模型，截图改页面走视觉模型。对客户端完全透明——Claude Code、Codex 等无需改任何配置，响应里回显的仍是客户端自己选的模型名。

01快速开始

三步，全程不用重启网关

  1. 侧边栏打开「智能路由」，勾选「启用智能路由」，在分类路由里给三个分类各选一个目标模型，点「保存配置」——保存即热生效。
  2. 在「路由模拟调试器」里粘一段真实 prompt 点「运行模拟」，确认判定结果符合预期（模拟器读的是已保存的配置）。
  3. 用客户端正常干活。想看实际效果，回面板在「路由审计」里点「刷新」。
保存前的唯一前置：目标模型要出现在对应 Provider 的模型列表里（配置方案页 → 探测模型）。分类下拉的选项、以及「目标模型是否已接入」的校验都取自这个列表；没探测过的模型选不到，硬填也会被判无效回退。

02判定顺序

这是固定契约，所有配置都围绕这八步起作用

1
强制模型
force_model 非空则直接用它，后面全部跳过
2
别名替换
model_alias_map 按入站名替换模型名
3
方案级重写
原有 ModelRewriter 档位规则照常执行
4
#MODEL: 标签
请求内容里的标签，命中即终止，只提取不修改原文
5
自定义规则
按配置顺序，第一条命中的生效
6
任务分类
复杂核心 → 视觉前端 → 常规兜底
7
默认模型
以上全部无结果时用 default_model
8
已接入校验
目标不在 Provider 模型列表 → 回退默认模型并记警告

生效端点：/v1/messages、/v1/responses、/v1/chat/completions。count_tokens 与 MCP 不做判定。总开关关闭时整层旁路，完全回到原有方案级重写路径，零行为变化。

03全局配置

总开关、强制、兜底、回退，四个参数管全局

enableRoute 启用智能路由
总开关。关闭 = 整层旁路。
forceModel 强制模型
填了之后所有请求都走它，分类、规则、标签全部失效。适合临时全局锁定，用完记得清空保存。
defaultModel 默认兜底模型
所有规则都没命中时用它；也是「目标模型校验失败」和「失败回退」的落点。建议填最稳的那个模型。
fallbackEnable 模型不可用自动回退
仅当上游返回「模型不存在」类 4xx 错误时，用默认模型重发一次。详见失败回退。

04模型别名映射

解决「客户端叫的名」和「后端实际的名」对不上

键 = 客户端入站模型名，值 = 后端实际模型名。例如 claude-opus-5 → glm-5.3。客户端发的 claude-code/ 前缀会先剥掉再匹配，所以 claude-code/claude-opus-5 也能命中键 claude-opus-5。

  • 别名在方案级重写之前执行——键按「客户端会发来的名字」写就行。
  • 别名只影响后续判定的起点，不影响最终路由结果：替换后的名字仍会走标签 → 规则 → 分类这条链。
  • 一般不需要配：方案页的 opus/sonnet/haiku 档位重写仍然在工作。别名是给它够不着的场景准备的（比如某个客户端发出非常规名字）。

05分类路由

分类特征内置不可改，只给每类选目标模型；没选的类不参与路由

判定按 复杂核心 → 视觉前端 → 常规兜底 的顺序：先看是不是复杂核心，不是再看是不是视觉前端，都不是就落常规。

complex_core 复杂核心任务

命中任一条件即判复杂核心：

  • 关键词（中英混合，大小写不敏感）：多租户、RBAC、行级权限、校区隔离、越权防护、财务结算、课时扣费、退费、转课、课消、排课引擎、事务一致性、资金分账、业务状态机、核心 Schema、架构设计、跨模块重构、安全审计、复杂事务 SQL、permission model、architecture design
  • 请求带 reasoning_effort=max，或 Messages 协议 thinking.budget_tokens ≥ 63999（Claude Code 开深度思考即触发）
  • 请求上下文估算超过 64k tokens 且未命中其他类

visual_frontend 视觉前端任务

  • 关键词：Vue、React、组件、表单、样式、UI、截图、Figma、切图、Playwright、视觉测试、页面还原、component、stylesheet、screenshot、frontend
  • 请求内容包含图片（Messages 的 image 块、Responses 的 input_image、Chat 的 image_url——截图改页面、多模态识别自动命中）

regular_dev 常规开发任务

以上两类都没命中就是它：CRUD、DTO、迁移、测试、脚本、文档……日常开发的大头。

扫描范围与成本上限：分类与关键词只扫 system 提示 + 前 2 条 + 最后 6 条消息（Responses 的 input、Chat 的 messages 同理），每段文本最多 4000 字符、总量 24,000 字符。路由信号几乎总在最近几轮对话里，这个窗口在省掉全量扫描成本的同时不影响实际判定——但意味着 #MODEL: 标签或关键词写在很老的中间消息里不会命中。

06自定义规则

关键词或正则 → 指定模型；优先级低于标签、高于分类

每条规则四个字段：

关键词 keyword
普通模式按子串匹配（英文小写化）；勾选「正则」后按正则匹配。
目标模型 targetModel
命中后转发的模型名。
正则 isRegex
正则模式。非法正则在面板里即时提示，保存后该规则被自动禁用并在保存结果里给警告，其余规则不受影响。灾难性回溯由 24k 扫描上限兜底。
启用 enable
关掉即跳过，配置保留。

规则按列表顺序判定，第一条命中即生效。想覆盖内置分类，把规则加在分类能命中之前就行——例如教培项目想让「对账」强制走强模型，加一条 对账 → glm-5.3 即可，不必等分类。

07#MODEL: 标签

单条请求临时指定模型，优先级仅次于强制模型

在 prompt 任意位置写 #MODEL:模型名，例如：

帮我细抠这段权限校验的边界情况 #MODEL:glm-5.3
（只对这一条请求生效，其余请求照常走分类）
  • 格式：#MODEL: 后跟模型名，允许字母、数字、_ . - /，中间可有空格；取第一个出现的标签。
  • 只提取、不修改你的 prompt 原文——标签会原样发给模型。
  • 优先级：低于强制模型，高于自定义规则与分类。强制模型非空时标签失效。
  • 标签仍要过第 8 步校验：目标不在 Provider 模型列表时回退默认模型。

08路由模拟调试器

不发真实请求，直接验证判定链

填入模型名、一段 prompt、可选 effort 档位，点「运行模拟」返回判定结果：目标模型、判定原因、命中规则、校验警告。它复用与网关同一套引擎与已保存配置，模型校验用所有已绑定网关方案的 Provider 模型并集。

改完配置必须先「保存配置」再模拟——模拟器读的是落盘配置，不读面板上未保存的草稿。判定结果与真实请求唯一的差别是审计：模拟不写审计记录。

09审计与复盘

每条请求一条决策记录，按 request_id 可追溯

真实请求经过智能路由后，面板「路由审计」点「刷新」可查（最新在前，内存保留最近 1000 条）。字段如下：

字段含义
requestId / timestamp请求标识与时间，同一次请求的回退重发共用同一 requestId
originalModel → aliasedModel → routedModel客户端原名 → 别名/方案级重写后的名字 → 最终路由结果，一眼看出每层改了什么
routeReason判定原因：force_model model_tag custom_rule complex_core / visual_frontend / regular_dev default_model passthrough validation_fallback fallback_retry
matchRule / thinkingEffort / inputTokens命中的规则 id、请求携带的 effort 档、估算输入 tokens
isFallback是否为失败回退的重发请求

记录脱敏由构造保证：只记上述元数据，不含 prompt 内容、不含任何密钥。同一份决策也会写进应用日志（系统设置 → 日志可查），双写不丢。

日常排查口诀：先看 routeReason。出现 validation_fallback 说明目标模型不在 Provider 列表里——回配置方案页重新探测，或改选列表内的模型。

10失败回退

仅「模型不存在」类错误才重发，避免无意义双倍计费

开启「模型不可用自动回退」后，满足全部条件才会用默认模型重发一次：

  • 上游返回 400 / 404 / 422，且错误信息含 model not found、does not exist、invalid model、no such model、unknown model、model_not_found 之一
  • 默认模型非空，且与当前请求的模型不同

不回退的情况：5xx（服务端挂了，重发同样会挂）、429 限流（换模型不解决限流）、网络错误、内容审核类 4xx（重发只会再被拒一次并计两次费）。回退发生在任何字节发给客户端之前，流式请求同样安全；回退结果（无论成功失败）就是客户端拿到的最终响应，并写入同 requestId 的第二条审计记录。

走故障转移链（failover）的请求不做模型回退——那条路径的语义是「换 Provider」，两个机制各管各的。

11推荐配置示例

双模型分工：强模型管核心与视觉，快模型管日常

以「教培管理系统开发，glm-5.3 + glm-5.3-flash」为例：

配置项值理由
defaultModelglm-5.3兜底与回退都落在这里，放最稳的
complexCoreglm-5.3架构/权限/财务/排课，教培域关键词内置覆盖
regularDevglm-5.3-flash日常 CRUD/测试/文档占大头，快且省
visualFrontendglm-5.3截图改页面依赖多模态质量；实测 flash 够用可降
fallbackEnable开flash 挂了自动用 glm-5.3 顶上

想省去手点，在「导入 / 导出」卡粘贴下面的 JSON，点「导入」再「保存配置」：

{
  "enableRoute": true,
  "forceModel": null,
  "defaultModel": "glm-5.3",
  "fallbackEnable": true,
  "modelAliasMap": {},
  "categoryRouteMap": {
    "complexCore": "glm-5.3",
    "regularDev": "glm-5.3-flash",
    "visualFrontend": "glm-5.3"
  },
  "customRules": []
}

日常最有用的两个操作：Claude Code 里开深度思考（effort=max）自动升到 glm-5.3，平时 flash 干活；单条请求想临时换模型就在 prompt 里打 #MODEL:glm-5.3。

12常见问题

配置保存了，但请求还是走原来的模型？

按顺序查：① 总开关是否开启且点过「保存配置」；② 对应分类是否选了目标模型（未配置的分类不参与）；③ 审计里 routeReason 是不是 validation_fallback——是则说明目标模型不在 Provider 模型列表，去配置方案页重新探测；④ 别名/方案级重写是否把名字改成了你没想到的值（看审计三段模型名）。

effort 深度思考什么时候触发升档？

Messages 协议 thinking.budget_tokens ≥ 63999 或 reasoning_effort=max、Responses 的 reasoning.effort=max。Claude Code 的深度思考开关即落在这些字段上。

#MODEL: 标签没生效？

三个可能：标签写在了扫描窗口之外（只扫 system + 前 2 条 + 最后 6 条消息，把标签写在最新一条消息里最稳）；强制模型填了值（优先级压过标签）；标签目标模型没过第 8 步校验（看审计 validation_fallback）。

正则规则勾了「正则」却不生效？

非法正则会在面板行内提示、保存后自动禁用该规则并在保存结果给警告——修正写法或关掉该规则。另外正则匹配的是小写化后的文本。

客户端会看到路由后的模型名吗？

不会。响应里回显的始终是客户端自己发的模型名（别名与路由结果都不外泄），/resume 等会话续接不受影响。

别名映射和方案页的档位重写（opus/sonnet/haiku）冲突吗？

不冲突，是串联关系：全局别名先替换，方案级重写后执行。一般档位重写已经覆盖常规命名，别名只在没有档位规则匹配时才需要配。

关掉智能路由会留下什么影响？

没有。总开关关闭后整层旁路，行为与从未开启过完全一致；配置保留在 state.json 里，下次开启原样恢复。审计记录也保留，可继续查询。
